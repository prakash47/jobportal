### `feature/recruiter-publish-draft` — recruiter Publish-from-draft (DRAFT→ACTIVE) · 2026-07-17

**Recruiter "Publish a saved draft" flow** (SRS §4.9). CLI merge to `develop` (`--no-ff`). **Recruiter-only** — `apps/web` + `apps/services` **byte-untouched** (`git diff develop…HEAD -- apps/web apps/services` empty); **no schema/migration/new feature-flag/shared-surface-lock**. Closes the gap the prior `feature/recruiter-draft-jobs` "Draft Jobs" list exposed: a saved DRAFT could be edited/duplicated/deleted but had **no path to go live** (edit is a PATCH that never changes status; close/reopen reject DRAFT; create(PUBLISH) makes a *new* job).

**API:** new **`POST /recruiter/jobs/:id/publish`** (bodyless — publishes the STORED draft as-is). `publish()` mirrors create()'s make-live gating: `assertPostingEnabled()` (reuses **`killswitch.recruiter_post_job`** — no new flag) → `resolveRecruiterContext()` (verified-work-email hard gate, SRS §4.9.5) → ownership 404 → reject non-DRAFT (400) → **validate the stored draft's mandatory fields (title ≥3 / description ≥10 / department / openings ≥1 / city) and 400 with the exact gaps BEFORE `quota.consume`** so an incomplete draft never burns a slot → moderation flag decides ACTIVE vs PENDING_MODERATION → consume quota → flip → side-effects (ES index + alerts + cache purge) + job-posted email (ACTIVE only). The **DRAFT→final flip is an atomic `updateMany({ where: { id, status: 'DRAFT' }, … })`** (the `delete()` pattern): only the request that actually wins the transition (count 1) keeps its slot + fires side-effects; a concurrent double-click/retry/second-tab sees count 0 and **refunds** its slot — no double-consume, no duplicate "your job is live" email. The catch path also refunds on a post-consume DB failure. `postedAt` is refreshed to the go-live moment (a stale draft shouldn't rank/date as old), and a **stale past `expiresAt` is cleared** so a freshly-live job isn't expired by the very next nightly sweep.

**Recruiter UI:** the Jobs list ⋮ menu gains a **Publish** item — own **DRAFT** rows only, rendered first (the primary draft action), hidden when the post-job killswitch is ON (L2, threaded as `publishEnabled` through `page.tsx`→`JobsTable`→`JobRowMenu` like `deleteEnabled`). It opens a confirm dialog via a new `JobStatusDialog` **`publish`** action (the dialog's generic `POST /recruiter/jobs/:id/<action>` already fits; the API's 400/429/503 message surfaces inline). `packages/ui/src/icons.ts` +`Send` (append-only barrel).

**Adversarial review** (3 lenses — correctness/security, frontend/react/a11y, regression/isolation — each finding independently verified by a refuter): **11 raised → 8 confirmed (3 refuted: an unreachable verification-gate bypass ×2 and a duplicate expiry finding), all 8 fixed.** (LOW) non-atomic status guard → double-click could double-consume + double-email → atomic `updateMany` + refund-the-loser; (LOW×2) no refund on the post-consume failure/lost-race paths → `quota.refund()`; (LOW) dialog copy promised "goes live immediately / appears in search" which is false under moderation → reworded flag-agnostic ("Once it goes live…"); (LOW) stale `expiresAt` not cleared → cleared if past; (LOW) comment falsely claimed parity with create(PUBLISH) → corrected (publish() is intentionally stricter); (LOW) update-throws path untested + (NIT) missing-fields test asserted only the type → added the refund/race/verified-gate/expiry tests + a message-content assertion. Also added the verified-email gate as defense-in-depth even though the two refuters proved it currently unreachable-to-bypass (drafts can only be created by a verified recruiter and verification is monotonic) — enforcing it at the make-live boundary is non-bypassable per CLAUDE.md §4.

**Gate (integrated, develop @ e73a405):** typecheck **11/11** · tests **5/5** (API **606** (+10) / web 186 / auth 17 / feature-flags 37 / observability 19 — the recruiter app has no unit-test harness, consistent with every prior recruiter PR) · build **4/4** apps. **Browser-verified** (real browser, demo recruiter Priya @ Nimbus): the Publish item shows only on own DRAFT rows (absent on an ACTIVE row); a complete draft → **ACTIVE** with `postedAt` refreshed to the publish moment + **quota 0→1**; an incomplete draft (no dept/city) → **400 "missing required fields: department, city"** shown in the dialog, stays DRAFT, **quota NOT consumed** (still 1); the atomic path re-verified after the review fixes; every fixture created was **deleted — DB restored to exactly 7 jobs**; **0 console errors**. (The transient Redis quota counter now reads 2/5 daily · 2/30 monthly from the two published-then-deleted fixtures — a TTL-reconciling counter, not DB job data; matches prior verification PRs that published/deleted jobs.)

**Deferred / follow-ups (by design):** a DRAFT→ACTIVE publish is now possible, but **create(PUBLISH)'s DTO still leaves `primaryCityId`/`functionalAreaId`/`openings` optional** — the wizard's Publish button gates them client-side, so via the UI you can't create an ACTIVE job without them, but a direct API `create({publishMode:'PUBLISH', title, description})` would produce a live job missing city/department/openings. `publish()` is deliberately stricter; tightening `CreateRecruiterJobDto` (a `publishMode==='PUBLISH'` refine) is a separate task. The best-effort quota refund is not transactional with the Redis counter (a double Redis failure could briefly leave a slot leaked until TTL) — accepted, matching the codebase's existing quota-reconciliation posture.
